# 个人英雄池与统计口径

实现：`crates/hero-pool`。普通统计读取当前账号的本地 `MatchRecord`；位置分析另读取已缓存的 `MatchRoleEvidence`，输出可解释的位置候选。英雄池配置按账号保存到 SQLite 的 `pool:ACCOUNT_ID` setting，已有数据可离线分析。

## 统计

每个英雄按 `(account_id, match_id)` 去重，再按比赛开始时间倒序统计。未来时间和负数时间不纳入。当前实现包含：总场次、结果已知场次、胜败场次、原始胜率、先验平滑胜率、Wilson 95% 区间、最近 20/50 场、最近 90/180/365 天、指定版本、时间加权胜率、有效样本量、平均 KDA/GPM/XPM 和完整阵容覆盖率。

历史页面的聚合包含所有已导入模式。推荐器会另行筛选标准模式并重新统计，因此英雄池页面的全模式场次可能高于推荐原因中的场次。模式筛选规则见 [推荐模型](recommendation-model.md)。

结果缺失不计为失败，也不进入胜率分母。最近 20 场表示最近 20 条比赛记录，不是向前寻找 20 条结果完整的比赛；结果已知场次单独显示。KDA 计算为每场 `(kills + assists) / max(deaths, 1)` 后取均值，不等于“总击杀助攻除以总死亡”。缺失字段不参与该字段的均值。

`current_patch=None` 时当前版本窗口为空。导入的玩家比赛投影目前没有可靠 `patch` 字段，不能把空值当作当前版本。界面尚未实现完整的逐版本统计比较。

## 样本量与时间

原始胜率保留其历史含义；1 胜 0 负仍可显示历史 100%，但必须与 1 场样本及宽区间一起解释。评分使用以 0.5 为均值、强度为 10 的 Beta 先验：`(wins + 5) / (known_results + 10)`。这是一组工程初始参数，没有经过用户历史回测优化。

时间权重为 `2^(-age_days / half_life_days)`，默认半衰期 180 天。有效样本使用 Kish 公式 `(sum(w))² / sum(w²)`。它只反映权重集中程度；很旧且同龄的 100 场仍可能有 100 个 Kish 有效样本，所以推荐器另用时间权重之和限制近期熟练度和证据等级。

Wilson 区间针对未加权二项结果，未处理版本漂移或同一玩家比赛间的相关性；它不是本局胜率区间。当前没有训练个人概率模型。

## 候选规则

| 模式 | 可用英雄 |
| --- | --- |
| 自动 | 自动建议集 |
| 手动 | 用户明确加入的集合 |
| 混合 | 自动建议集与用户加入集合的并集 |

三种模式都应用明确排除名单和位置限制。桌面新配置默认 `selected_role=0`，表示自动考虑有证据支持的位置：分别计算一至五号位候选，再按英雄 ID 合并、去重并排序。用户可以选择具体位置缩小范围，也可以保留自动模式。`0` 是桌面编排选项，不是第六个游戏位置；核心推荐函数仍接收具体的 1—5。

桌面先以位置分析的 `suggested_roles` 补充用户配置，再得到 `effective_pool`。覆盖规则如下：

| `pool.roles` 中某英雄的值 | 行为 |
| --- | --- |
| 没有这个英雄键 | 使用当前自动推断结果 |
| `[2, 3]` 等非空数组 | 用户覆盖，使用明确指定的位置 |
| `[]` | 用户明确不允许任何位置，自动推断不能重新加入 |

“恢复自动推断”删除对应键。明确排除名单在三种英雄池模式中都优先生效。缺少可用自动证据、也没有手动覆盖的英雄不会进入推荐；这时可以继续补充详情，而不是要求用户为所有英雄先填位置。

自动建议的初始门槛为总使用至少 5 场，或近 90 天使用至少 3 场；排序考虑总场次的对数、近期场次的对数和平滑胜率，最多保留 20 位英雄。这是可解释的初始规则，不代表达到门槛就已经熟练，也未经过优化验证。

用户优先级范围为 `[-1, 1]`，对应推荐评分最多 ±5 分。它只改变合格候选的顺序，不能绕过明确排除、位置、已选或禁用规则。非零整数英雄 ID 与位置 1–5 在配置入口校验；游戏目录合法性由桌面命令层校验。

## 自动位置分析

入口为 `analyze_roles(records, details, now)`，当前规则版本为 `team-farm-lane-v1`。只分析已结束的标准模式比赛，按当前账号和比赛 ID 去重。不同账号不会混合；详情中的目标槽位、英雄及可用账号标识必须与个人历史匹配。

`MatchRoleEvidence` 来自 OpenDota 比赛详情，保存来源、采集时间和用户所在队伍五人的英雄、槽位、分路、经济及补刀证据。不保存队友账号、昵称、聊天或整个响应。早期字段是 `gold_t`、`lh_t` 在第 10、11、12 分钟的均值；缺少任一分钟时保留未知。上游 `position_est` 也是推断，不作为真实位置标签。字段定义可对照 [OpenDota MatchResponse](https://github.com/odota/core/blob/master/svc/api/responses/MatchResponse.ts)，分路与上游推断的实现见 [compute.ts](https://github.com/odota/core/blob/master/svc/util/compute.ts)。

规则使用同队五人的相对资源排名，不使用静态英雄 Carry/Support 印象：

1. 优先使用全队完整的 10—12 分钟经济和补刀均值；否则尝试全队终局 GPM 与补刀。缺失指标不补零。
2. 经济与补刀均排在前三时，形成核心候选，再结合分路标签区分一、二、三号位。财富第一不会直接变成一号位；缺少分路或标签冲突时保留 `[1, 2, 3]`。
3. 两项均排在后两位时，保留 `[4, 5]`，不按财富高低或分路强行区分两种辅助职责。
4. 使用并列排名区间；指标冲突或并列跨越核心/辅助边界时，本场不累计位置支持。只有分路标签时可以显示提示，但不据此自动指定位置。

每个英雄的每个建议位置至少需要 **3 场独立、符合上述规则的比赛证据**。这里的“有效”是规则资格，不是 Kish 有效样本量，也不是准确率验证。一场比赛可以同时支持多个候选位置，不能把各位置支持场次相加当作总场数。两个核心候选、四/五号位并列或跨场位置变化均可保留，不强制只选一个位置。

详情补充优先近期比赛，再按英雄轮流取样，避免常玩英雄占满预算。桌面每次最多尝试 240 场未缓存详情；继续执行会跳过已缓存比赛。它不是随机或完整历史抽样，不能用候选支持场次推断全历史的精确位置占比。解析数据可能很稀疏，缓存有详情也不代表双指标足够或位置可区分。

报告中的 `total_matches` 是去重后的输入总数；`eligible_matches` 是符合模式和时间条件的场数；`analyzed_matches` 是取得有效队内证据的场数；`unknown_matches = eligible_matches - analyzed_matches`。每英雄 `coverage` 以该英雄符合条件的场数为分母，表示分析覆盖率，不是识别准确率。`detail_matches` 仅表示已有对应缓存。

`strength` 的 `unknown`、`limited`、`moderate` 是工程证据提示。终局经济会受崩线、比赛进程和职责变化影响，只标记为有限；早期双指标与单一分路候选一致时可标为中等。当前没有经过人工位置标签评估或概率校准，任何级别都不是“此英雄有多少概率担任该位置”。

## 当前边界

- 自动位置需要足够的同队详情证据；补充数据可能受公开范围、解析覆盖、请求预算和限流影响。未知结果不会自动变为某个位置。
- 分路、KDA、经济数据仅展示已知字段；不会把 `lane_role` 直接当成一至五号位。
- 手动加入且没有历史的英雄，在明确配置允许位置后可以进入候选；其胜率使用先验、熟练度按零、可信度标为有限。
- 自动规则、半衰期和先验强度尚无足量真实数据的效果评估。
- 位置支持按符合规则的独立场次数累计，当前没有单独应用时间衰减或版本校正；较早的职责变化可能仍影响候选。
- 一至五号位的独立胜负表现、跨版本稳定性指标、逐英雄完整克制/协同矩阵页面尚未完成。自动位置候选不代表已建立分位置胜率模型。
- 历史回测尚未重建每个时间点的位置推断，也不自动合并当前 `effective_pool`，详见 [回测限制](recommendation-model.md#回测协议)。

测试覆盖去重、未知结果、未来记录、字段空值、KDA 数值安全、非法 ID、排除名单，以及位置分析的账号隔离、槽位核对、并列排名、指标冲突、样本门槛与缺失早期数据。自动化测试证明规则按定义执行，不证明位置推断准确率或胜率提升。
