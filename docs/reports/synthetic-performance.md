# 合成历史数据性能诊断

2026-11-03 UTC，在 Linux release 构建上测量了 10,000 场和 50,000 场明确标注为 `synthetic` 的历史数据。当前负载中，完整比赛及阵容读取比英雄聚合和单位置推荐耗时更长。复用 SQLite 连接可避免仅为读取设置而重复执行数据库打开与 `quick_check`。

这是本地业务模块的有限负载诊断，不是真实个人数据分析，也没有测量截图识别、Windows 捕获、悬浮窗、GPU 或 DOTA2 FPS。合成的胜负、版本和位置配置不用于产品默认值或效果宣传。

## 方法与环境

- 系统：Ubuntu 22.04，Linux 6.8.0-106-generic x86_64，glibc 2.35。
- CPU：AMD Ryzen 9 9950X，32 个逻辑 CPU。使用普通共享主机，没有绑定 CPU、隔离其他负载或清空操作系统缓存。
- 编译器：Rust/Cargo 1.97.1；`cargo build --locked --release -p dpda-debug --example synthetic_performance`。
- 代码基线：`e67f205409fdc8982cdb834e2c0ddb349916089c`，工作树包含尚未提交的诊断程序及其他并行工作。原始环境报告另存被测模块和二进制的 SHA-256。
- 每阶段采样五次，表中单列第一次结果，再给出后四次的中位数与范围；五个样本不足以报告稳定的 P95。

生成器使用固定种子 `4450444153594e54`、固定统计时间 `2026-11-03T00:00:00Z`、单一合成账号、唯一比赛 ID、`game_mode=22`、`duration=2400`，所有比赛均在统计时刻之前结束。每场保存四名队友和五名敌方英雄，阵容随固定生成规则变化。1 万场对应 9 万条阵容记录，5 万场对应 45 万条。

使用本地英雄目录中的 25 个稳定 ID，配置五个手动位置池，每个位置五个候选；这些位置分配仅为覆盖执行路径，不表示英雄的实际位置建议。推荐上下文包含两名队友、三名敌人及四个未确定槽位。每次均断言读回比赛数、阵容人数、英雄统计数和推荐数量，防止空数据或过滤掉全部记录导致虚假的低耗时。

每个规模在独立进程中创建临时 SQLite，退出时删除，没有读取已有用户数据库，也没有网络请求。先测生成与插入，再释放生成数据、重开数据库并测读取/统计/推荐。未运行历史回测。

## 测量结果

单位为毫秒。单元格格式为“首次 / 后续中位数〔最小–最大〕”。首次测量发生在同一进程刚写完数据库之后，不是磁盘冷启动测量。

| 操作 | 10,000 场 | 50,000 场 |
| --- | --- | --- |
| `Database::open`，含 `quick_check` | 10.740 / 10.467〔10.388–10.656〕 | 48.494 / 47.350〔47.296–48.174〕 |
| 复用连接读取一个设置值 | 0.027 / 0.002〔0.002–0.003〕 | 0.035 / 0.002〔0.002–0.003〕 |
| `Database::records`，含双方阵容 | 22.959 / 22.461〔22.280–22.679〕 | 119.803 / 116.619〔116.138–122.725〕 |
| `hero_pool::aggregate` | 0.656 / 0.553〔0.522–0.598〕 | 3.672 / 3.090〔3.051–3.326〕 |
| `recommend`，位置 1 | 2.698 / 1.697〔1.687–1.771〕 | 15.814 / 11.515〔10.102–12.602〕 |
| `recommend`，位置 2 | 1.702 / 1.686〔1.676–1.692〕 | 10.536 / 9.984〔9.619–10.582〕 |
| `recommend`，位置 3 | 1.688 / 1.675〔1.672–1.743〕 | 9.698 / 9.423〔9.171–9.683〕 |
| `recommend`，位置 4 | 1.683 / 1.691〔1.685–1.694〕 | 10.028 / 9.545〔9.266–9.741〕 |
| `recommend`，位置 5 | 1.698 / 1.713〔1.691–1.729〕 | 9.431 / 9.540〔9.286–9.908〕 |

`recommend` 内部还会执行可用历史筛选和重新聚合，上述推荐耗时已包含这些步骤。五个位置是分别执行的场景；桌面只针对当前选定位置推荐，不能把五行相加称为一次 BP 更新耗时。

| 整个诊断进程 | 10,000 场 | 50,000 场 |
| --- | --- | --- |
| 合成数据生成 | 1.562 ms | 7.842 ms |
| 数据库创建与迁移 | 4.600 ms | 4.927 ms |
| 单事务插入 | 461.066 ms | 2,188.629 ms |
| 主数据库文件大小 | 9,027,584 bytes | 45,719,552 bytes |
| 峰值 RSS | 15,828 KiB（15.46 MiB） | 49,944 KiB（48.77 MiB） |
| 整个进程墙钟时间 | 0.69 s | 3.37 s |

RSS 来自 `/usr/bin/time -v` 的进程高水位，包含合成数据生成、SQLite 插入与后续所有测量，不是桌面应用的稳态内存，也不能归因给某一个阶段。计时器直接包裹已构建的可执行文件，不包含 Cargo 编译。

## 判断与边界

5 万场负载下，数据库打开和检查的后续中位数为 47.35 ms，复用连接的单个设置查询约 0.002 ms。因此，采集线程仅为了定期读取设置而重新打开数据库，会重复执行与数据量相关的检查。当前采集线程复用连接的调整与该测量结果一致；本诊断没有修改产品代码，也没有测量调整前后实际游戏开销。

完整比赛和阵容读取约 116.62 ms，是本次所测单步骤中较大的持续成本。后续优化可先检查重复读取是否必要，例如只在个人数据变化时刷新缓存；是否值得实现，应结合真实桌面调用频率再决定。本报告没有把不同规模的合成结果外推为低配置电脑性能保证。

`Database::records` 当前使用主记录查询和批量阵容查询，本报告不是逐场查询实现的前后对比。没有测量真实磁盘冷读、网络导入速度、多个账号、多个并发读写者、数据库损坏恢复或长期运行。

## 复现

```bash
python3 scripts/benchmark-synthetic.py
```

包装脚本构建 release 示例，顺序执行 1 万场和 5 万场，输出原始 JSON、`time -v` 日志、环境及源码指纹。默认目录为 `artifacts/synthetic-performance/`，不进入版本控制。已有相应 release 构建时可用 `--skip-build`；`--rounds` 支持 3–10。

单独执行某个规模：

```bash
cargo build --locked --release -p dpda-debug --example synthetic_performance
/usr/bin/time -v target/release/examples/synthetic_performance --matches 50000 --rounds 5
```

实现位于 [synthetic_performance.rs](../../crates/debug-cli/examples/synthetic_performance.rs) 与 [benchmark-synthetic.py](../../scripts/benchmark-synthetic.py)。示例只接受 100–50,000 场，不提供用户数据库路径参数；它不会运行二次复杂度的回测。

验证：release 构建通过，示例的严格 Clippy 检查通过，两种规模的所有断言通过并正常退出；没有新增依赖。
